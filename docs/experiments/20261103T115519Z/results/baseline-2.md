# 全文检索选型研究报告

**研究截止：2026-11-03T11:55:19Z**

## 结论先行

**建议把 SQLite FTS5 作为首个试点基线，以 Meilisearch 做中文检索效果对照，第3周依据实测定型；Tantivy 保留为条件性替代。**这不是认定 SQLite 性能最好，而是：在两名开发者合计每周2人日、8周共16人日的约束下，同库事务、统一备份和较少运行组件，更有利于完成来源版本、引用和恢复闭环。

反对这一建议的主要理由是：**FTS5 默认不提供中文词级分词，也没有默认拼写容错**；接入分析器、处理混排和改进排序可能抵消部署优势。Meilisearch 若能显著减少这些工作，即使增加独立服务，也可能总成本更低。Tantivy 原生适配 Rust、查询组合灵活，但“嵌入式”不等于无需自行完成搜索产品能力。

**证据限制：**本报告未进行联网核验或团队数据实验。功能讨论以 SQLite 3.45.3／FTS5、Tantivy 0.22.0、Meilisearch 1.8.0 自托管开源版为历史基线，不建议直接部署旧版。截止日最新维护版本、安全修复和许可证变化未知；第1周必须复核并锁定实际版本。下列未版本化官网文档可能变化，不能把其新增功能倒推到上述基线。

## 一、三种方案的能力与边界

### SQLite FTS5：适合事务优先、搜索需求受控的最小工具

**默认能力：**嵌入式全文索引，支持布尔、短语、前缀查询，以及 BM25 排序、摘要和高亮。默认 `unicode61` 分词器不做中文词级切分，连续汉字可能形成长词项；不能因为支持 Unicode 就认为中文检索已解决。[1]

**自行接入：**可在 Rust 端接入中文分析器，对索引与查询使用相同的切词、大小写和混排规则，再将预分词文本交给 FTS5。原始正文必须另存，不能用插空格后的文本代替证据。词典和分析器版本需要记录。另一条路是自定义 FTS5 tokenizer，但会增加接口与构建维护成本。

`trigram` 提供三字符子串检索，**不是中文分词替代品**；不足三个 Unicode 字符的全文查询无法靠它覆盖，常见两字词尤其需要验证。[1]

**更新与失败：**普通内容 FTS 表可增删改，并与来源表在同一 SQLite 事务内提交。典型问题包括查询语法未转义、索引与查询切词不一致、长事务阻塞写入；采用外部内容表却遗漏同步机制，还会造成索引与正文不一致。试点宜先用普通内容表，接受文本副本换取简单性。

### Tantivy：适合需要嵌入式、可编程检索的场景

**默认能力：**Rust 搜索库，提供倒排索引、BM25 和可组合查询。0.22.0 的默认分析链使用简单切词、小写化和长词过滤，并非中文词级分析器；连续中文长串还可能触发长词过滤。[2]

**自行接入：**中文 tokenizer、领域词处理、查询构造、结果呈现和服务接口均由应用负责。模糊查询等构件存在，不等于默认具备完整拼写纠错体验。自定义 tokenizer 必须在写入和查询侧保持一致。

**更新与失败：**通常按稳定文档 ID 编排“删除旧项＋加入新项”，然后 `commit`；搜索 reader 还需要 reload 才能看到提交。未提交写入不能算已索引。常见问题是忘记 reload 导致结果陈旧、分析器注册不一致、后台合并争用 CPU／磁盘，以及逻辑删除后空间没有立即回收。[2]

它避免独立服务，但没有消除索引生命周期、恢复和检索语义的工程工作。没有复杂查询需求证据时，不宜仅因宿主是 Rust 就优先选择。

### Meilisearch：适合用现成搜索体验换取服务运维

**默认能力：**上述版本的常规官方构建包含中文专用分词，并提供前缀搜索、拼写容错和内置排序规则；这减少了应用侧工作，但中文、英文、代码标识符混排的实际质量仍未知。其默认规则排序也不能与 BM25 分数直接横比。[3]

**自行接入：**应用需要管理主键、字段配置、异步任务、错误展示、重试和来源版本关联。领域专名、繁简、拼音及两字词效果不能由“支持中文”自动推定通过；也不能默认拥有与自定义 tokenizer 相同的控制能力。

**更新与失败：**写入、更新、删除是异步任务，拿到 `taskUid` 仅表示接受请求，不代表成功或可搜索；必须检查终态。全量替换与局部更新语义不同，误用可能遗漏字段。任务失败、积压、索引内存压力，以及重试覆盖较新数据，是需要处理的失败模式。[4]

**共同未知：**三者在团队语料上的相关性、尾延迟、索引体积、峰值内存和恢复时间均未测。公开基准的硬件、页长、配置与查询分布不同，不能直接外推为本工具的生产结果。

## 二、最小架构：来源可信度先于搜索引擎

范围限定为**受控网页导入、单一搜索入口、来源版本查看与引用导出**；不同时建设通用爬虫、浏览器插件、协作或智能问答。按没有现成检索实现计入工作量。

以 SQLite 作为权威存储，保存：

- 稳定文档 ID、不可变来源版本 ID、URL、抓取时间；
- 原始 HTML、固定的抽取正文、内容哈希、抽取器版本；
- 当前版本指针、删除状态及索引配置版本。

最小实现可把快照一并存入 SQLite，避免文件与数据库之间的双重提交；是否改用外部文件，应由实际体积决定。重抓或重新抽取产生新版本，不覆盖旧正文。默认只搜索当前版本，历史版本保留用于复核，而非同时建设历史全文检索。

**引用不能只有 URL 或搜索高亮。**引用应绑定：

`来源版本 ID + 固定正文中的 UTF-8 字节区间 + 原文片段校验值`

界面显示来源 URL、时间和版本，并能定位到保存的正文；不承诺实时网页仍有相同内容。分词、归一化后的偏移不能直接当原文坐标；尚未建立可靠映射时，应定位到已保存段落，而非伪造精确字符位置。三种引擎都不会自动保证这些应用级约束。

采用 FTS5 时，来源更新、当前指针和索引更新放入同一事务。采用 Tantivy 或 Meilisearch 时，SQLite 同事务写入待索引事件，再由单一工作器顺序投递；使用稳定 ID、事件序号和幂等重放，防止旧事件覆盖新版本。Tantivy 提交并刷新 reader、Meilisearch 任务成功后，才能标记已可搜。

返回命中时仍须核对版本和删除状态：**允许显示“索引更新中”，不允许把旧命中套在新正文上。**这能避免错引，但不能消除外部索引暂时漏结果的一致性窗口。

## 三、崩溃、持久化与迁移

**SQLite：**WAL 模式允许读写并行，但同一时刻仍只有一个写者；长读事务可能妨碍 checkpoint，导致 WAL 增长。建议来源保存使用 `synchronous=FULL`，明确“已保存”的提交边界；`NORMAL` 在 WAL 下并不提供相同的断电持久性。实际保障仍依赖操作系统和存储正确实现同步写入。[5]

备份使用 SQLite 在线备份接口等一致性机制，不应在数据库运行中只复制 `.db` 而忽略 WAL。[6] 来源表与 FTS 同事务可缩小恢复面，但磁盘损坏仍需要独立备份。

**Tantivy：**`commit` 是索引提交边界，未提交更新可能需要重放；恢复后还应核对应用事件进度，而不是仅判断索引能否打开。它与 SQLite 没有共同事务。删除和段合并也意味着必须预留重建及合并空间。[2]

**Meilisearch：**使用 LMDB 持久化，但服务数据库、异步任务与应用 SQLite 属于不同提交域。重启后需要查询任务并对账。官方区分同版本恢复使用的 snapshot 与用于迁移的逻辑 dump；不能假设 snapshot 可直接跨版本恢复，也不能假设任意版本间 dump 导入都无需中间步骤。[3][7]

共同策略是：**索引可重建，来源版本不可随意重写。**分析器、字段 schema 或引擎版本变化时，从权威来源构建新索引，验证后切换，保留回滚路径。升级前锁定程序、配置和词典版本并演练恢复。强杀进程测试不等同断电测试，未测试的故障类型必须保留为未知。

## 四、许可证、资源与数据边界

历史基线中，SQLite 属公有领域；Tantivy 0.22.0 与 Meilisearch 1.8.0 为 MIT。中文词典、绑定及其他依赖仍需独立审查；不能把开源自托管版的许可结论套到云服务或后续企业扩展。[3][8]

成本不能只算许可费：

- **FTS5：**运行组件少、事务与备份统一；代价在中文分析、搜索体验和文本副本。
- **Tantivy：**无独立服务；代价在检索逻辑、索引管理、构建升级与调优。
- **Meilisearch：**增加进程、密钥、健康检查、任务监控和升级流程；但可能节省中文、前缀与容错功能开发。额外服务不是否决条件。

10万份网页不能直接换算成内存需求：页长分布、最大页面、历史版本数量、字段、更新峰值和磁盘性能都重要。Meilisearch 的索引内存参数、Tantivy 的 writer 预算都不能视为整个进程内存硬上限；内存映射也不表示数据全部驻留或没有内存压力。[2][9]

服务应显式绑定回环地址，保护管理密钥，并关闭不需要的遥测、验证非预期外连。[9] 所有方案都需要文件权限、磁盘与备份保护；保存的 HTML 应隔离展示，不能直接执行脚本。“从搜索中删除”不等于物理擦除，隐私删除须同时考虑历史快照、索引、日志和备份保留期。

## 五、8周试点、验收与退出

以下安排是**16人日预算，而非完成保证**。只统一导入格式、版本 ID 和评测脚本，不先建设三引擎通用框架。

| 周次 | 每周2人日的主要产出 |
|---|---|
| 第1周 | 复核维护版本、依赖许可与安全配置；统计样本页长，冻结查询集及验收线。 |
| 第2周 | FTS5 与 Meilisearch 最薄对照，仅完成导入、查询和版本 ID 返回。 |
| 第3周 | 复核失败案例并定型；必要时投入最多1人日做 Tantivy 定向探针，不增加总预算。 |
| 第4周 | 完成不可变来源存储、版本查看与引用定位。 |
| 第5周 | 完成新增、更新、删除及失败可见性；按所选方案实现事务或事件重放。 |
| 第6周 | 逐级扩大数据，测查询、写入、内存和磁盘峰值。 |
| 第7周 | 演练进程崩溃、磁盘满、备份恢复及升级回滚。 |
| 第8周 | 本机打包、操作文档、缺陷修复与最终验收；保留缓冲，不新增功能。 |

### 建议验收线

**以下数字均为建议，不是实测结果或行业标准；第1周结合数据和硬件确认后冻结。**

1. **相关性：**拟建40条任务查询，中文20、英文10、混排10，覆盖两字词、专名和错拼；每条事先标定至少一个应召回来源版本。各组一半调试、一半留出。留出20条中 Top5 命中至少18条，各语言组不少于80%。这是小规模任务验收，不是总体召回率估计。
2. **响应与资源：**在目标10万份、真实页长分布、单用户负载下，热态端到端 Top20 查询 p95≤300毫秒；冷启动单独报告。检索相关进程合计峰值 RSS≤4 GiB，无 OOM 或持续换页。磁盘预算须覆盖来源、索引、备份及重建并存。
3. **更新与引用：**正常负载下单条更新、删除5秒内可见；100组版本变更检查中，引用定位与原文校验全部通过，删除项不作为当前结果返回。隐私清除与普通搜索删除分别验收。
4. **恢复：**20次随机进程强杀后，已确认保存的来源版本无丢失，索引可以重放或重建。若采用每日独立备份，建议磁盘损毁恢复点目标为24小时、恢复至可搜索目标为60分钟；同盘备份不能支撑磁盘损毁承诺。

没有取得10万份代表性数据，就只能报告样本规模通过；复制页面或合成数据可以测资源压力，不能证明真实相关性或完整容量。

### 选择和退出条件

- **选 FTS5：**全部硬门槛通过，中文分析维护可控，Meilisearch 没有显示足以抵偿服务成本的任务收益。
- **选 Meilisearch：**全部硬门槛通过，并且是唯一达标候选，或至少挽回两个留出失败任务且无关键回退；逐条解释收益，不把小样本差异包装成统计显著性。
- **转 Tantivy：**出现前两者难以满足的明确查询或分析器需求，定向探针证明可行，且剩余工期足够。未做完整测试，就不能宣称它性能较差。
- **退出或缩范围：**错引版本、不可恢复、持续超内存预算均不能靠更换宣传指标放行。第3周仍无法定型，应停止三线扩张，重新约定规模或高级搜索范围；来源正确性与恢复能力不降级。若还必须从零建设大规模抓取系统，应另计预算。
