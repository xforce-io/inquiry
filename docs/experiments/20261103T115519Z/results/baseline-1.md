# 全文检索选型报告：先验证 SQLite FTS5，保留有条件切换

## 一、结论与证据边界

**建议将 SQLite FTS5 作为默认试点，而非已经胜出的生产方案；第2周设选型关口，同场验证 Tantivy 和 Meilisearch，随后只加固一个方案。**

支持这一方向的主要依据不是性能，而是架构：来源版本、引用定位和检索索引可以在同一个 SQLite 事务内更新，减少跨存储一致性、服务管理及备份路径。两名开发者合计每周2人日，8周总预算只有 **16人日**，这种简化值得优先验证。

反对依据同样明确：FTS5 默认中文处理不足，预分词、查询处理和相关性调试可能吃掉节省的工时。Tantivy 的可定制分析器可能更合适；Meilisearch 的现成中文处理和搜索体验也可能使总开发成本更低。**不能仅因 Meilisearch 是独立服务而排除它。**

研究截止线为 **2026-11-03T11:55:19Z**。本报告未联网核验该日最新发布，也没有团队实测。为避免混版，能力比较采用 **SQLite 3.45.3、Tantivy 0.22.0、Meilisearch v1.8.0** 的历史基线；这不是建议上线旧版。滚动文档只是复核入口，截止日的最新版本、漏洞状态和兼容变化均属未知，试点第一周必须确认实际部署版本。[1][2][3]

## 二、能力与适用边界

### SQLite FTS5：一致性简单，中文能力需要补齐

启用 FTS5 的 SQLite 构建提供全文索引、BM25 函数、短语、布尔及前缀查询；应用仍需显式选择排序方式。默认 `unicode61` 按字符类别识别词元，**不会把连续中文自动切成中文词**。内置 trigram 是子串检索工具，不等同于中文分词：不足三个 Unicode 字符的全文查询不能匹配；某些短 `LIKE/GLOB` 模式会退化扫描。[1]

建议试点在应用层统一处理索引文本与查询，例如接入 `jieba-rs`，另存原始正文。这属于自行接入，不是 FTS5 默认能力；领域词、英文缩写、型号和混合输入的效果仍需验证。[11] 不宜在16人日内先开发复杂的自定义 tokenizer 扩展。

普通 FTS 表支持 SQL 新增、更新和删除，可与来源数据同事务提交。若使用 external-content 表，源表变更不会天然同步到索引，需自行维护触发器及初始构建。典型失败包括漏同步、写锁竞争、大事务、长读导致 WAL 增长和磁盘耗尽。首版建议使用普通内容 FTS 表，接受一定数据重复，暂不引入 contentless 或 external-content 的同步分支。[1][6]

### Tantivy：适合需要更多检索控制、仍希望嵌入 Rust 的场景

Tantivy 是 Rust 检索库，不是开箱即用的搜索服务。它提供 BM25、查询解析和可组合的分析器，但默认分词流程不能代替中文词切分；中文分析器、词典以及索引与查询端的一致配置由应用负责。拥有模糊查询构件，也不等于已经具备完整的容错搜索体验。[2]

常见更新方式是按标识删除旧文档，再加入新文档；应用必须保证标识和操作顺序，不能假定主键自动去重。写入需要 `commit` 才进入持久提交边界，查询读者刷新后才看见新视图。典型失败包括重复文档、已提交但读者尚未刷新、索引与来源库不同步，以及段合并造成的资源峰值。[2]

适合 FTS5 在相关性或查询表达方面确有不足，而团队能承担分析器、索引生命周期和备份管理的情况；“原生 Rust”本身不是性能证据。

### Meilisearch：减少搜索产品层开发，但增加服务边界

上述版本基线内置前缀搜索、错字容忍和排序规则，并通过 Charabia 提供中文专用处理，不要求应用先安装中文分词插件。它的排序体系不能与 FTS5、Tantivy 的 BM25 分数直接比较；支持中文也不代表短词、简繁、专名及中英夹杂的相关性已经达标。[3][4]

文档新增、更新、删除等操作采用异步任务。HTTP 请求被接受不等于索引更新成功，应用必须检查任务终态和错误。设置变更可能带来重索引；忽略任务失败、积压和索引峰值，是典型风险。[5]

它适合能以默认能力明显提高真实任务成功率，或减少自行实现搜索功能的场景。代价是服务启动、版本升级、访问控制、资源监控及与来源库的跨系统一致性。

**共同未知：**领域词和混合检索效果、索引体积、导入速度、查询尾延迟及恢复时间。目前没有证据认定任何方案在本团队数据上最优。

## 三、最小架构与来源版本

建议架构为：

**导入网页快照 → SQLite 权威数据 → 一个可重建检索索引 → 简单本地界面。**

首版只做导入、关键词查询、打开冻结正文和复制引用；不做动态网页浏览器采集、全站爬虫、向量检索、多用户或复杂重排。不能假设团队已有这些组件。

每个来源版本至少保存：

- `version_id`、来源 URL、抓取时间；
- 原始响应快照、冻结正文及各自内容哈希；
- 提取器版本、稳定段落标识和正文中的字符区间。

正文提取规则改变时，生成新文本版本，不覆盖已经被引用的正文。正式引用包含版本标识、段落或字符区间和引文校验信息；从冻结正文读取，**不能把搜索高亮、分词后的词串或当前在线网页当作引用事实源**。承诺定位的是保存的正文，不是完整复现动态网页。三种引擎都不会自动保证这一契约。

FTS5 路径中，来源版本与索引在同一事务更新。若改选 Tantivy 或 Meilisearch，则在 SQLite 事务内同时写入待索引任务；消费者可重试地更新索引，在确认提交或任务成功后记录进度。崩溃可能导致重复执行，因此更新和删除必须可重复执行而不产生重复结果。

搜索结果回源校验版本及删除状态，防止旧索引误冒充当前正文；这可以避免错误引用，**不能消除索引延迟导致的漏检**。界面应分别显示“索引中”“无结果”和“失败”。已有引用仍打开原版本；若用户要求永久删除，引用应明确失效，而不是跳到新版。

## 四、持久化、恢复与迁移

**SQLite：**同库事务最容易覆盖来源与索引的一致性。WAL 配合 `synchronous=FULL` 可增强提交耐久性，但仍依赖操作系统和存储正确履行同步承诺；`NORMAL` 下掉电可能丢失最近已提交事务，不能与普通进程崩溃混为一谈。WAL 不是备份，直接复制正在使用的主数据库文件可能遗漏 WAL 内容。应使用 Backup API 或一致性备份方式，恢复后分别检查数据库、FTS 索引和引用关联。[6][7]

**Tantivy：**以成功提交为恢复边界，未提交批次须允许重放；提交不自动完成 SQLite 与索引之间的事务。备份应取得一致的已提交索引视图，不能随意复制正在变化的目录。首版更稳妥的退路是从权威数据重建，但重建耗时必须测量，不能把“能重建”当作“恢复足够快”。[2]

**Meilisearch：**请求、任务成功和应用确认是不同状态。它提供 snapshot 和 dump；snapshot 面向同版本恢复，dump 用于迁移场景，但仍需核对来源版与目标版的兼容要求，不能承诺任意跨版导入。[5][8]

三者均应记录引擎版本、索引结构、分词器及词典配置。分析器或词典改变后，通常需要重新建索引。升级优先采用“备份权威库—构建新索引—校验—切换”，保留旧程序和旧索引以便回滚；来源库结构迁移需另行验证。双索引、备份和合并期间的磁盘峰值也要纳入预算。

## 五、许可证、资源与安全成本

上述基线中，SQLite 核心为公有领域，Tantivy 和 Meilisearch 开源核心采用 MIT 许可证；Rust 绑定、分词器、插件及未来选定版本需分别审查，不能把核心许可证推及整个依赖树或云服务。[2][3][10]

“10万份网页”不足以推出内存或磁盘需求。正文长度、原始快照大小、历史版本数量和检索单元数量都可能改变规模。SQLite 的缓存、Tantivy 的写入预算、Meilisearch 的索引内存设置也不是同一种限制。尤其 **Meilisearch 的索引内存配置不等于整个服务的硬性内存上限**；搜索、缓存及其他组件仍消耗资源。[9]

应比较总投入：接入与调参工时、升级、备份、故障处理、磁盘冗余和日常维护。当前无法给出可靠货币成本或生产容量。官方示例及公开基准的硬件、语料、分词、查询和冷热缓存条件不同，不能直接外推成本团队结果。

安全上，SQLite/Tantivy 主要依赖文件权限和应用入口；Meilisearch 应显式绑定回环地址、配置密钥并限制权限。三者均不应被假定默认提供磁盘加密。快照、备份和日志包含敏感内容，应限制访问；关闭不必要遥测并检查外连，不能仅凭“自托管”断言零外发。[9] 原始 HTML 不执行脚本，导入大小和查询工作量设上限。逻辑删除不代表旧段、WAL 或备份已被物理擦除。

## 六、16人日的8周试点

下列样本数、工时分配和阈值均是**建议，不是既有测量**；第1周允许依据真实任务调整一次，随后冻结。

| 时间 | 人日 | 交付与关口 |
|---|---:|---|
| 第1周 | 2 | 锁定候选版本及依赖；确认数据来源、磁盘预算和引用契约；准备样本与查询 |
| 第2周 | 2 | 三者各做最小导入/查询实验，记录接入工时、相关性和资源；选择一个 |
| 第3–4周 | 4 | 完成来源版本、索引更新、检索、正文查看及引用闭环 |
| 第5–6周 | 4 | 扩至真实规模；测更新/删除、资源峰值、强杀恢复及积压重放 |
| 第7周 | 2 | 备份恢复、升级/回滚演练，形成简短操作文档 |
| 第8周 | 2 | 真实任务验收、修复与缓冲；不追加非核心功能 |

初筛建议使用 **2,000份有代表性的不同网页、60条真实查询**，中文、英文、中英混合各20条，其中一半留作不调参的验收集。纳入两字中文词、专名、缩写、型号和短语。三者只共用输入与评测输出，不开发三套完整产品。

### 建议验收门槛

1. **相关性：**各类留出查询至少8/10在前5条中出现人工确认的相关正文。样本很小，只是试点门槛，不足以证明总体优劣。
2. **引用：**抽查100条引用均能逐字回查到固定版本；来源更新后旧引用不变；检索删除后不再返回该来源，永久删除则明确报引用不可用。
3. **交互：**在真实10万份网页上，暖查询端到端 P95≤500毫秒；稳态单页新增/删除在权威提交后10秒内完成可见性变化。另报冷缓存及后台导入结果，不只测空闲引擎。
4. **资源：**应用与搜索服务合计峰值 RSS≤5GB，并记录系统缓存和交换情况，不发生 OOM 或持续交换；磁盘峰值不超过第1周冻结的预算。
5. **恢复：**至少10次覆盖关键提交边界的进程强杀，不丢失已确认的权威数据、不产生错误引用；恢复可查≤5分钟，备份恢复加重放≤30分钟，全量重建≤2小时。强杀不等于掉电测试，未测故障类型不得宣称通过。
6. **维护：**第7–8周记录的例行人工维护≤30分钟/周，累计开发不超过16人日。

### 选择与退出条件

- **保留 FTS5：**相关性、引用和资源门槛均通过，中文接入工作能留在预算内。
- **转 Tantivy：**它在同一评测中解决了 FTS5 的具体不足，且增加的分析器与生命周期管理工时可承受。
- **选 Meilisearch：**它是唯一通过关键搜索任务的候选，或现成功能节省的工时足以抵偿服务维护，并通过内存、恢复和安全验收。均达标时，按实记开发工时及注明假设的后续维护成本择优。

第6周仍有来源错配或恢复丢失，不上线；所有方案均超过资源或人力预算，则缩小容量或功能，而不是宣布“优化后应该能用”。若没有代表性的10万份数据，只能验收已测规模，不能靠复制样本补齐数量。

**最终决策还缺四类证据：真实语料字节分布、中文任务相关性、峰值资源与恢复实测、实际部署版本的兼容及安全核验。** 在这些证据出现前，SQLite FTS5 是低复杂度起点，不是已证实的最终答案。
