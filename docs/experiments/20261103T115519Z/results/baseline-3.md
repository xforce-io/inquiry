# 全文检索方案决策报告

**研究截止：2026-11-03T11:55:19Z**

## 结论先行

**建议把 SQLite 作为来源版本的唯一事实库，以“FTS5＋应用预分词”为首选试点；首两周同时验证 Tantivy、Meilisearch，过门槛后只维护一种检索实现。**这不是已经证明 FTS5 最快、中文最好或成本最低，而是在总计 **16 人日**的预算下，优先验证能减少跨存储一致性工作的方案。

支持这一建议的依据：FTS5 可与来源记录共用事务、备份和部署单元；单用户无需服务端并发能力。反对依据：FTS5 默认中文分词不足，预分词、混合查询和相关性调校可能抵消嵌入式部署的收益。**若 Meilisearch 的中文与交互能力在目标语料上明显减少开发工作，且资源、恢复测试合格，应接受独立服务；若 Tantivy 在必要的查询控制或资源指标上胜出，且接入工作能落入剩余预算，也应改选。**

关键未知包括正文长度、历史版本数、更新率、磁盘性能、中文专名分布，以及三者的实际相关性、内存峰值和恢复时间。10 万份文档本身不足以判断容量。

**证据边界：**本报告未联网核验截止日最新版。技术比较以 SQLite 3.46.0、Tantivy 0.22.0、Meilisearch 1.9.0 为历史版本锚点；滚动文档仅供机制复核，不将后续特性倒灌入旧版，也不建议直接部署这些旧版。拟用版本、许可证和安全公告须在首周重新确认。

## 1. 三种方案的能力与边界

### SQLite FTS5：最短一致性路径，但中文不是开箱即用

- **默认能力：**嵌入式全文索引、BM25、前缀查询、摘要和高亮。默认 `unicode61` 并非中文词法分词器，连续汉字通常形成长词元，中英连写也可能影响切分；不能把“支持 Unicode”理解为中文检索已解决。`porter` 是可选英文词干处理，不是默认中文方案。[1]
- **需要自接：**建议应用将中文分词后的检索文本单独保存，索引和查询使用同一套分词、规范化与词典版本，原文保持不变。这样可避免试点阶段编写 SQLite 自定义 tokenizer 接口，但必须测试短语语义和混排。`trigram` 可支持子串检索，却不是中文词法替代：少于三个 Unicode 字符的全文查询不能匹配；某些 `LIKE` 模式会退化为扫描。[1]
- **更新与失败：**普通 FTS 表支持增删改；外部内容表不会自动与正文同步，必须由触发器或应用事务维护，已有数据需回填。漏维护、删除时旧内容不一致、查询语法错误、写锁竞争及 WAL 增长都是典型问题。不要混淆传统 contentless 表与 SQLite 3.43.0 才加入的 contentless-delete 表；本试点不依赖后者。[1]

适合检索要求可控、来源与索引需紧密一致的本地工具；默认不提供完整拼写容错体验。

### Tantivy：Rust 内嵌且控制力强，但不是现成搜索产品

- **默认能力：**Rust 检索库，提供倒排索引、BM25及查询构件。0.22.0 的默认 tokenizer 包含简单切分、小写化和长词过滤，并不提供中文词法分词；连续中文可能切分不足，长串还可能被过滤。[3]
- **需要自接：**中文 tokenizer、词典、混合查询规则，以及完整的搜索接口和交互语义。模糊匹配等查询构件不等于默认启用了用户友好的容错。标题权重、字段查询较可控，但收益与开发成本均待验证。
- **更新与失败：**通常按稳定主键先删旧文档、再加新文档，并在提交后发布；主键唯一性由应用保证。`commit` 与 reader 刷新是不同边界，提交成功不代表所有读者立即看见。漏刷新、重复文档、未提交变更丢失、合并阶段资源峰值，以及分词配置不一致都需防范。[3]

适合确有 Rust 内嵌、查询定制需求且愿意承担索引生命周期工作的场景；不能仅凭 Rust 宿主就认定它最省工。

### Meilisearch：现成功能较多，代价是进程和异步一致性

- **默认能力：**独立搜索服务，提供前缀、容错及多级排序规则；默认排序不能等同于 BM25。它使用 Charabia，包含中文专用分词路径，比上述两者更接近中文开箱可用，但专名、繁简和混排效果仍须实测；英文容错能力也不能直接推定为中文错字处理效果。[4][5]
- **需要自接：**显式主键、可搜索字段、过滤配置、任务状态追踪及来源版本关联。部分更新与整文档替换语义不同，应固定一种并测试。
- **更新与失败：**写入、删除等通过异步任务执行；收到任务编号或 HTTP 成功响应不等于已可搜索。任务失败、积压、重试旧更新覆盖新状态，以及调整设置引发重索引，都是实际维护边界。[5]

适合其现成功能能替代足够应用工作的情况。独立服务不是排除项，但必须把任务队列、配置、认证和备份算入成本。

## 2. 最小架构：先保证来源，再选择索引

最小闭环为：

**导入网页 → 保存不可变版本 → 更新检索 → 搜索 → 打开冻结正文 → 复制可定位引用。**

SQLite 保存来源版本、最新版本指针、删除状态和必要的同步账本。每个版本至少包含：版本 ID、原 URL、采集时间、原始字节及哈希、冻结正文、提取器版本。这里的快照保证保存的 HTML／正文可回溯，**不承诺重现脚本和外部资源构成的完整网页**。

正常检索先只索引每个来源的最新有效版本，避免历史副本挤占结果；旧版本仍可被引用。命中必须携带来源版本 ID，不能只返回 URL。引用保存“版本 ID＋冻结正文中的块或 UTF-8 字节区间”，打开时核对引用文本。索引的高亮、词元位置或格式化摘要仅用于展示，不能直接当作原始 HTML 的稳定定位。

分词器、词典和索引 schema 属于**索引代次**；改变它们应重建索引，而不是改写已引用正文。URL、采集时间和哈希支持回溯与内部完整性检查，不自动构成网页在某时刻公开存在的第三方证明。

一致性采用最小必要机制：

- **FTS5：**来源记录、最新指针及 FTS 更新放入同一 SQLite 事务；读取命中和版本信息时使用一致的读事务。
- **Tantivy／Meilisearch：**来源提交与待同步任务同事务落库；消费者按来源序列化、幂等重放，索引提交或任务完成后才确认同步。它们与 SQLite 之间没有天然分布式事务。
- 查询端检查命中的版本与删除状态；陈旧命中应过滤或标明，不能偷偷替换成另一版本再生成引用。逻辑删除移出检索但保留已引用版本；物理清除则明确显示引用不可用。

界面只需导入、搜索、版本查看和引用复制；显示“待索引／失败可重试”，查询失败不得伪装成零结果。多用户、向量检索、分布式和通用爬虫调度不进入本轮。

## 3. 崩溃恢复、持久化与迁移

**SQLite：**正确维护的 FTS 与来源数据共享事务恢复。建议试点显式采用 WAL 与 `synchronous=FULL`，同时验证目标文件系统行为；WAL 配合 NORMAL 在断电后的最新提交持久性与 FULL 不同。长读事务可能阻碍 checkpoint，造成 WAL 增长。备份使用在线备份 API 或受控关闭流程，不可只复制正在运行的 `.db` 而忽略 WAL。[2]

**Tantivy：**提交是关键持久化边界，未提交操作不能视为已保存。重启后读取有效提交，利用来源账本补齐差异；reader 刷新另行验证。跨版本索引兼容性不能假定成立，升级前必须检查目标版本说明并试迁移。[3]

**Meilisearch：**内部数据库事务与任务系统不提供跨应用数据库的一致性。恢复后须检查任务状态并核对实际结果。快照主要用于同版本恢复；dump 是逻辑导出、导入时需要重建索引，适用于官方支持的迁移路径，不代表任意版本可互相导入。[6]

共同原则是：**索引可重建，来源库不可被索引替代。**迁移先备份来源库，建立新代次索引、校验后切换，并保留相容的旧二进制与旧索引。分词、字段规则和提取策略变更分别记录，避免“升级后结果变了却无法解释”。进程强杀测试不等于断电或坏盘测试。

## 4. 许可证、资源与维护成本

SQLite 核心声明为公有领域；Tantivy 0.22.0 与 Meilisearch 1.9.0 的历史许可为 MIT。[8] **这不能替代对截止日拟用发行版、企业功能、Rust 绑定、SDK、分词器及字典的逐项核对。**无许可费用不等于没有维护成本。

成本判断只能先作架构推断：

- FTS5 少一个独立进程和跨库同步环节，但中文处理、FTS 一致性检查仍需开发。
- Tantivy 少一个网络服务，却增加 tokenizer、reader、提交和合并管理责任。
- Meilisearch 可能减少搜索功能开发，却增加服务启动、任务监控、升级和认证维护。

8 GB 是否足够目前未知。应测量来源库、所有索引、后台合并、分词、备份及检索并发时的总峰值；预留旧新索引并存的磁盘空间。Tantivy writer 预算、Meilisearch 索引内存配置都不等于整个进程的 RSS 硬上限，mmap 地址空间也不等于实际常驻内存。[3][7] 公共基准的机器、文本长度、语言及持久化条件不同，不能外推为本团队吞吐、成本或恢复时间。

数据默认留在本机。Meilisearch 显式绑定回环地址并配置认证，核查并关闭不需要的遥测；三者的原文、索引和备份均采用受限文件权限。本地快照查看器禁用脚本和远程资源，防止保存网页触发执行或外发请求。搜索语法、文档大小和批量任务应设边界；SQL 参数化不能替代 FTS 查询语法处理。[7]

## 5. 选择条件、8 周安排与退出门槛

先比较是否满足硬门槛，再比较相关性、实际接入人时和恢复操作成本：

| 选择 | 应满足的条件 |
|---|---|
| FTS5 | 应用预分词能在预算内满足中文与混合检索要求，性能、引用和恢复均过关；条件相当时优先 |
| Meilisearch | 目标语料上的质量或功能接入收益足以抵偿服务维护，且资源和任务恢复过关 |
| Tantivy | 有必要的查询控制需求，或实测证明 FTS5 的资源／延迟问题可由它解决，并能承担自接能力 |
| 暂不定型 | 三者均未通过，或只有代理语料结果；不能据此宣布支持目标规模 |

### 16 人日安排

排期不假设存在可复用检索实现。

- **第 1—2 周，4 人日：**锁定候选版本、许可和安全状态；整理代表性语料及查询集，做三个最小适配器，只允许一次有边界调参。第 2 周末选主方案和唯一后备，不建设三套生产实现。
- **第 3—4 周，4 人日：**完成不可变来源版本、选定索引、增删改和引用闭环；冻结功能范围。
- **第 5—6 周，4 人日：**运行目标规模测试、故障注入和备份恢复；修复一致性、资源与质量问题，第 6 周作继续／切换决定。
- **第 7—8 周，4 人日：**验收、安全与升级回滚演练、运行手册；其中预留 2 人日用于后备方案或缺陷，不增加功能。

### 建议验收值——不是已有测试结果

以下均为**试点假设和待确认阈值**：

1. **质量：**初筛可用约 3,000 份代表性网页；人工准备中文、英文、混合查询各 10 条，覆盖两字词、专名、数字等。每组至少 8 条查询的前 10 个结果包含已确认相关来源。该小样只作筛选，不代表总体召回率。
2. **规模与响应：**胜出方案必须在 10 万份目标分布网页上复验，记录总正文量和长度分布。导入并发搜索时热查询 p95≤500 ms、普通增删改可见延迟≤10 秒；另报告真实冷读结果，不把进程重启视为清空系统缓存。
3. **资源：**应用与检索进程合计峰值常驻内存建议≤5 GB，无 OOM 或持续换页；统一共享页计量口径，同时记录系统可用内存、磁盘峰值和完整导入时间。
4. **一致性与引用：**连续 100 次更新／删除后，无旧版本错误覆盖、重复主键或已删除来源的正常检索命中；抽查 50 条引用全部定位到原冻结文本。
5. **恢复：**20 次写入中强杀后，已确认保存的来源版本零丢失，索引能够追齐；建议重启恢复查询≤5 分钟、派生索引全量重建≤4 小时，并完成一次备份恢复和盘满处理演练。

若第 2 周中文效果仍需大规模自研，停止继续投入该候选；第 6 周资源、引用或恢复硬门槛失败，且剩余预算不足以修复，则启用已筛选后备。两者仍失败，应缩减容量或交付明确受限的原型，不能放宽来源正确性来宣称完成。若真实语料未到位，代理集只能证明链路可运行，**不能签署“10 万网页可用”的验收结论。**
