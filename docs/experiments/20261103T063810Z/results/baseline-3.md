# 决策报告：以 Playwright 为主，按风险引入浏览器 Agent

**研究截止：2026-11-03T06:38:10Z。**  
资料边界：未进行实时联网核验。以下引用支持历史结果与技术机制，不代表已核实截止时点的最新产品能力、价格、排行榜或数据处理条款。

## 一、结论先行

**未来8周，不应把约30条流程整体迁移给 Agent。建议采用“自有回归确定性执行、第三方操作按风险混合”的方案。**

- **自有产品回归：**以 Playwright 为发布门禁，优先覆盖高损失流程。Agent 可辅助编写测试、诊断失败，但不能在运行时擅自改变验收条件。
- **第三方后台：**先评估官方 API；稳定、重复的流程用脚本；页面偶发变化、低风险且能独立验证结果的任务，试用 Agent 规划、Playwright 执行的混合方案。
- **不可逆或高影响操作：**试点期间，生产付款、批量删除、权限变更的最终提交仍由人完成。

支持这一结论的是现有 TypeScript、GitHub Actions 与 Playwright 的适配性，以及明确断言、版本控制、失败追踪带来的可审计性。[1][2] 反对依据也成立：脚本会因页面变化产生维护成本，Agent 可能减少长尾流程的适配工作；混合方案自身又增加模型、审批和策略校验成本。因此，**混合只是有条件的候选，不是每条流程都必须调用模型。**

关键未知包括：30条流程的归属与频次、现有人工耗时、失败损失、第三方认证限制，以及公司允许发送给模型的数据范围。目前没有依据承诺具体生产成功率或节省金额。

## 二、三种方案的边界

Playwright 是浏览器执行与测试工具；Agent 是观察、规划和选择动作的决策层。Agent 可以通过 Playwright 执行操作，Playwright MCP 就是这种组合的公开实例。[3] 两者不是同层互斥产品。

| 方案 | 自有产品回归 | 第三方后台操作 |
|---|---|---|
| 确定性 Playwright | 默认选择。固定输入、业务断言、可复现失败，适合作为发布门禁 | 适合高频、稳定且获准自动化的流程；页面变化时明确失败 |
| 浏览器 Agent 主导 | 适合探索、生成测试草稿，不宜独自裁定回归通过 | 适合沙箱、只读、低损失探索；不适合无监督高权限写入 |
| 混合 | Agent 提建议，经评审形成版本化测试；执行时不自动“修好”失败 | Agent 处理变化和定位，确定性执行器控制动作、权限、提交与验证 |

“纯 Agent”也需要浏览器工具；其区别在于运行时由模型决定路径。混合方案必须明确哪些步骤允许模型决定，否则只是给不确定系统套了一层脚本。

替代方案包括官方 API、平台批处理和人工检查清单。**低频任务若预计节省的人工不足以抵消建设、维护和审批，保留人工往往更合理。**托管浏览器只是部署选择，可能减少运维，但会增加会话数据托管、费用和供应商依赖，不能自动提升业务正确性。

## 三、可靠性证据：能证明什么，不能证明什么

### 1. 工具机制不等于生产成功率

Playwright 的自动等待会检查可见性、稳定性、是否可接收事件等条件；官方建议使用面向用户的定位方式、测试隔离和自动重试断言。[1][2] 这些机制能减少时序和定位问题，**但按钮能点击，不代表订单已正确创建、权限已正确变更。**

自有产品应使用明确业务后置条件，必要时通过只读 API 或后端状态交叉核验。第三方任务则使用记录编号、独立查询等证据；没有可靠验证渠道的结果只能记为“未证实”，不能接受模型自述成功。

### 2. 公开基准与厂商成绩不可直接外推

WebArena 的2023年原始论文报告，最佳 GPT-4 Agent 成功率为14.41%，人类为78.24%；OpenAI 在2025年 CUA 发布材料中自报 WebArena 成绩58.1%。[4][5] 后者支持“Agent 值得试验”，前者也不能用来断言今天的 Agent 仍只有早期水平。

但这些数字均不是本团队生产测量。网站版本、任务分布、DOM或截图接口、认证方式、尝试次数、时间预算与评分器不同，不能把数字直接横比，更不能当成未来8周的预期成功率。厂商演示、工具调用成功率和经过筛选的案例，也不等于完整业务闭环的可靠性。

### 3. 典型失败及对策

- **脚本失败：**定位器漂移、共享账号串扰、测试数据污染、异步状态未完成、会话过期。对策是独立数据、稳定定位、业务断言和脱敏追踪，而非增加固定等待。
- **Agent 失败：**误认对象、漏约束、提前结束、循环尝试，或被网页内容诱导偏离任务。不能让同一个模型既操作又作为唯一裁判。
- **共同失败：**网络、第三方限流、验证码、MFA及权限变化。不得绕过认证控制；无法继续时转人工。
- **虚假改善：**重试把首轮失败藏起来，或“自愈”修改了本该检测的产品行为。Playwright 会区分重试后通过的 flaky 测试；试点也应分别报告首次与最终结果。[6]

真实产品缺陷导致的正确阻断，不应算自动化不稳定；但必须保留记录并经复核分类，不能为了通过率删除失败。

## 四、成本：先记完整账，再比较工具账单

建议采用：

**总成本＝建设、维护、审批、故障处置工时×内部小时成本＋CI/浏览器费用＋模型费用＋存储审计费用。**

仅作容量情景：若第一天起每次发布都运行30条流程，8周、每周两次发布，共480次首轮执行；**假设**每条耗时1—3分钟，则为480—1,440浏览器分钟，尚未包含 PR 检查、重试、环境启动和跨浏览器矩阵。这不是实测成本，也不等于供应商计费分钟；并行主要降低等待时间，未必降低账单。

Agent 费用应按完整任务记录输入、输出、图像、工具调用与重试账单，不能用一次简短问答的价格估算。失败后人工接管、检查错误副作用的时间同样计入。

建议暂设**全队每周8人时、8周64人时**的试点投入上限，包含建设与复核；由一名主责、一名备份分担。这是预算，不是完成全部30条自动化的承诺。超限先减覆盖，不削减权限与结果验证。

比较时使用“该类任务全部尝试成本÷独立确认安全完成数”，并将人工接管完成另列。只有混合方案在同等预算下提高安全完成率，或在可靠性不下降时降低完整成本，才值得保留。

## 五、最小架构与安全控制

不建设多 Agent 平台。沿用 GitHub Actions、Playwright Test，加一个与发布凭据隔离的 Agent 执行环境即可：

**任务配置 → 脚本，或 Agent 提出结构化动作 → 策略校验 → 浏览器执行 → 独立结果验证 → 完成或人工接管。**

任务配置列明允许域名、账号、对象范围、动作、后置条件及时间、步数、费用上限。策略必须在执行器调用前检查，不能只写在提示词里。模型不得任意调用 shell、访问内网或扩大任务权限。

### 权限与数据边界

- 自有回归优先使用测试环境和合成数据；第三方使用专用最小权限账号。**只读应由账号权限保证，而不是模型承诺。**
- 不可信 PR 代码与持有生产凭据的任务分离；GitHub Actions 的令牌权限按任务最小化。[9]
- 网页、邮件和弹窗均视为不可信数据，不能更改任务规则。官方 computer-use 指南也强调隔离和提示注入风险；人工审批并不能消除此风险。[8]
- 认证状态文件可能包含可冒用身份的 Cookie 等信息，不得提交仓库。[7] 凭据由执行器管理，不进入模型提示词。
- 截图、DOM和追踪文件可能含客户信息或令牌，应最小采集、脱敏、限制访问和留存。模型及托管浏览器的保留、训练使用、区域和合同条款未核验前，不上传真实客户敏感数据。

### 写入、审批与失败恢复

低风险、可撤销写入若需批准，应展示并绑定具体租户、对象、字段、金额或数量及有效期；执行前重新核对状态，变化则重新审批。生产不可逆操作仍由人最终提交。

超时后必须区分“未执行”和“结果未知”。后者先查询实际状态，禁止盲目重试。支持幂等键的 API 应使用幂等机制；只有 UI 且不能确认提交结果时，转人工核对。

任务状态至少包含待执行、执行中、待审批、已验证完成、失败、结果未知。保留停止开关和撤销凭据能力，但须承认：**停止执行只能止损，不能回滚已经发生的付款或删除。**

## 六、8周试点安排

| 阶段 | 工作与交付 |
|---|---|
| 第1—2周：建立基线 | 盘点约30条流程，按归属、频次、损失、读写权限分级。选首批约10条高价值自有回归及1—2类第三方低风险任务；记录现有人工/脚本耗时和结果，确定独立成功判据、预算与审批人 |
| 第3—4周：先稳定回归 | 建立隔离数据、稳定定位、业务断言和脱敏追踪。先非阻断运行，稳定后进入发布门禁；Agent 只给测试草稿或失败分析，不自行改变断言 |
| 第5—6周：受控比较 | 在相同、可复位的代表实例上，比较脚本、受限 Agent 与混合方案；固定版本和预算，交错执行顺序。写操作只在沙箱或获授权测试账号演练；加入页面变化、会话失效、超时和注入测试 |
| 第7—8周：收敛决策 | 观察四次发布，复核首次失败、遗漏缺陷、审批负担和完整成本。逐类决定保留脚本、扩大混合或回归人工；交付值班说明、停止开关和人工兜底清单 |

对照应使用同类任务、相同权限和相同业务判据。历史回放、沙箱与生产结果分别报告；不得为凑样本在真实后台重复产生业务副作用。

## 七、验收、选择条件与退出条件

以下是**建议在第一阶段固定的试点门槛，不是已有测量结果或总体可靠性保证**。

### 验收指标

1. **自有回归：**首批选定流程全部有业务后置条件；在经确认正常的版本上累计至少100次执行，观察到的首轮通过率不低于98%。预设10个覆盖关键断言的故障应全部阻断；不得通过 Agent 修改断言来恢复绿色。
2. **第三方低风险任务：**至少30个代表性实例，观察到的无人介入、安全完成率不低于90%；需要审批的写任务单列，不冒充无人成功。审批与故障接管分别计时，并纳入总成本。
3. **安全：**试点不得发生越权写入、错租户操作或敏感数据泄漏；预设注入和超范围动作测试应被阻断。零事件是准入要求，不是“已证明安全”。
4. **可持续性：**最后两周维护与故障接管不超过每周4人时；混合方案相对同类对照，应满足“同预算更可靠”或“同可靠性更便宜”。扩大覆盖仍受64人时试点预算约束。

所有指标按流程类别报告分子、分母、首次结果、最终结果和人工介入，不把步骤或重试当新增独立样本。统计上，即使100次独立试验全部成功，95%置信水平下失败率上界仍约为3%；同站点、同版本的重复执行还有相关性，证据更弱。样本不足时只能得出探索性结论。

### 退出与最终选择

- 出现越权、错对象写入、数据泄漏或策略被绕过，立即停用相关自动执行，撤销凭据并人工核查。
- 连续两周维护超预算，或第8周质量、成本门槛未达标，撤掉 Agent 自动执行，保留脚本或人工流程。
- 不稳定回归退出自动阻断时，必须恢复对应人工发布检查，不能静默取消验收。
- 第三方任务过于偶发、无法形成有效样本时，不扩大权限，也不宣称生产可靠性已得到验证。

**最终应购买的是可验证的业务闭环，而不是更高的演示完成率。8周的成功，是获得一批可信发布门禁、少量边界清晰的第三方自动化，以及继续或停止的本团队证据。**
